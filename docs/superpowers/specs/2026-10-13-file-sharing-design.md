# File Sharing — Design

Date: 2026-10-13
Status: Draft, awaiting review
Scope: sub-project 1 of 2 (backend limits, `shared/`, web UI, CLI). The MCP server is sub-project 2 and out of scope.

## Goal

Let a sender attach a file (up to 5 MiB) instead of text. Files follow the same model as text messages:

- Encrypted client-side with AES-256-GCM. The key stays in the URL fragment.
- The server stores only ciphertext + IV in Redis with a TTL and deletes it atomically on first read.
- The server learns nothing about whether a message is a file, its name, or its type.
- PostgreSQL metadata/history, Slack/email notifications, and logs never contain a filename, type, or content.

## Non-goals

- Files larger than 5 MiB, chunked upload, or blob storage outside Redis.
- MCP server (sub-project 2; `mcp/` has only `main.go` and does not build).
- Changing how the encryption key is stored server-side (see "Known issues").
- Multiple files per message (zip them first).

## Wire format

No API, `Message` struct, or Redis schema change. A file message is a normal message whose plaintext is an envelope:

```
VNSHFILE1\n
{"name":"<string>","type":"<mime string>","size":<int>}\n
<raw file bytes>
```

- The whole envelope is encrypted with the existing scheme: AES-256-GCM, 96-bit IV, base64 ciphertext/IV.
- Text messages are unchanged byte-for-byte, so existing links and older clients keep working.
- Decrypt side: if the plaintext starts with `VNSHFILE1\n` it is parsed as a file; otherwise it is text. A text message that happens to start with that exact prefix and then fails header parsing is treated as text. One that parses as a valid header is treated as a file (accepted, negligible risk).
- `size` must equal the number of data bytes; a mismatch is an error.
- Header line is limited to 4 KiB (4096 bytes before the first `\n`; the newline search only looks that far). Senders refuse to build a longer header ("File name or type is too long" / `ErrHeaderTooLarge`).
- A valid header (anything else is text), identical in Go and JS and pinned by the `unpack` cases in `shared/crypto/testdata/vector.json`:
  - the header bytes are valid UTF-8 (a leading BOM is kept, so it fails JSON parsing) and parse as a JSON object;
  - keys match exactly and case-sensitively (`name`, `type`, `size`); for a duplicate key the last value wins;
  - `name` and `type` are JSON strings (lone UTF-16 surrogate escapes become U+FFFD);
  - `size` is a JSON number with an integral value in `[0, 5242880]`; integral floats such as `1.0` and `1e0` count (JavaScript numbers cannot tell them apart from `1`), while fractional, negative, over-limit and out-of-range values are not.

### Filename handling (both JS and Go)

`SanitizeFilename(name)`: take the base name after the last `/` or `\`; remove control characters (< 0x20, 0x7F) and `:*?"<>|`; trim leading/trailing spaces and dots; cap at 255 bytes without splitting a UTF-8 sequence; if the result is empty use `vanish-file`. The sanitized name is used for every write/download. The raw name is never used.

## Limits

- Client enforces: file non-empty and ≤ 5 MiB (5,242,880 bytes) before encrypting.
- Base64 overhead (~33%) plus JSON fields means the create request body is ≤ ~7.5 MB. Backend wraps the create route body with `http.MaxBytesReader` at 8 MiB and returns 413 on overflow.
- nginx (unified image and any proxy config) must allow the same body size via `client_max_body_size 8m` on `/api/`. To verify during implementation: where the nginx config lives (grep of the repo found no `client_max_body_size`; the default 1 MB would block files).
- The backend cannot distinguish files from text, so the limit applies to all messages.
- Open item for implementation: Redis memory. Up to 5 MiB is held until read/expiry. Not capped per user in this iteration; documented in `docs/ARCHITECTURE.md`.

## Frontend (`frontend/src`)

### `lib/crypto.js`
- Add `encryptBytes(bytes, key)` and `decryptBytes(ct, iv, key)` operating on `Uint8Array`. Existing `encrypt`/`decrypt` unchanged in behavior.
- `arrayBufferToBase64` converts in chunks (e.g. 32 KiB via `String.fromCharCode.apply`) instead of per-byte concatenation.
- `base64ToArrayBuffer` normalizes URL-safe characters (`-`→`+`, `_`→`/`) and re-pads, fixing keys generated by the Go CLI (which uses `base64.URLEncoding`). This is a bug fix required for CLI→web interop.

### `lib/fileEnvelope.js` (new)
- `MAX_FILE_BYTES`, `packFile(file) -> Uint8Array`, `unpackEnvelope(bytes) -> {kind:'file',name,type,data} | {kind:'text',text}`, `sanitizeFilename(name)`.

### `lib/download.js` (new)
- `saveBlob(data, name)`: Blob (always `application/octet-stream`; the sender's MIME type is never used, because a same-origin blob a browser renders could run script) → object URL → temporary `<a download>` click → revoke URL. Returns a function that can re-trigger the save while the page is open.

### `components/CreateMessage.jsx`
- Text / File toggle above the input.
- File mode: file picker with drag-and-drop, shows name and size, remove button.
- Rejects empty or over-limit files with a clear error before any encryption.
- Submit enabled condition depends on mode. Recipient, TTL, Slack/Email notification flow unchanged. Success screen wording becomes kind-neutral.

### `components/RetrieveMessage.jsx`
- Same single button and burn-on-fetch behavior; the page cannot know the kind beforehand (the `exists` check returns no kind). Button label becomes neutral ("Reveal & Destroy Message").
- After `decryptBytes` → `unpackEnvelope`: text → clipboard as today; file → `saveBlob`.
- Decrypted content stays in the handler closure; never enters React state or the DOM. Only the sanitized filename is shown, on the burned screen.
- Burned screen wording depends on kind. For files, a "Save again" button re-triggers the download from the in-closure Blob until the user leaves (covers browsers that block a download triggered after an `await`).
- If saving fails after the burn the file is lost, as with a failed clipboard write today. Documented in the UI copy.

## Shared Go library (`shared/`)

### `crypto`
- Add `EncryptBytes([]byte)` and `DecryptBytes(ciphertext, iv, key) ([]byte, error)`. `EncryptMessage`/`DecryptMessage` become thin wrappers; behavior unchanged.
- New `envelope.go`: `PackFile(name, mime string, data []byte) ([]byte, error)`, `Unpack(plain []byte) (*Payload, error)`, `Payload{Kind, Name, Type, Data}`, `SanitizeFilename`, `MaxFileBytes`.
- Key encoding stays `base64.URLEncoding` for generated keys; decoding already accepts both.

### `client`
- `SendMessage` unchanged.
- Add `ParseMessageURL(url) (id, key string, err error)`.

## CLI (`cli/`)

- `vanish send <email> --file <path> [--ttl ...]`: stat first and refuse empty or > 5 MiB; read; MIME type from extension (fallback `application/octet-stream`); `PackFile` → `EncryptBytes` → `SendMessage`. `--file` and an inline message are mutually exclusive.
- New `vanish get <url> [-o <path>] [--force]`:
  - Parses ID + key from the URL; before fetching, verifies the output path is writable (for files, the destination directory exists and the target does not exist unless `--force`), so a doomed write does not burn the message.
  - Fetch (burns) → `DecryptBytes` → `Unpack`.
  - Text → stdout. File → `-o` path, or sanitized name in the current directory; created with mode `0600`.
  - Success is reported only after the write completes.
- Update `printHelp` and `cli/README.md`.

## Testing

Shared vector: `shared/crypto/testdata/vector.json` holds a fixed key, IV, filename, MIME type, file bytes (including a NUL byte and non-ASCII), and the expected ciphertext. Both the Go tests and the frontend vitest read it.

- **Frontend (vitest):** envelope round trip incl. binary; plain text passes through `unpackEnvelope` as text; `sanitizeFilename` cases (`../../x`, `a\b`, control chars, empty, very long, multibyte at the cap); size/empty rejection; size-mismatch error; URL-safe key import; shared vector decrypts and unpacks.
- **Go:** envelope round trip; shared vector; `SanitizeFilename`; limits; `ParseMessageURL`; `get` write-path against `httptest` incl. overwrite refusal, `--force`, pre-check failure leaving the message unburned.
- **Backend:** create with body just under and over the limit → 201 / 413 (existing `tests/unit` style; note storage tests need Redis).
- Manual end-to-end: web→web, CLI→web, web→CLI, each with a binary file and a text secret.

## Known issues (out of scope, noted)

- `CreateMessage` stores `req.EncryptionKey` in PostgreSQL message metadata "for recipient link generation" (`backend/internal/api/handlers.go:82`). Ciphertext (Redis) plus key (Postgres) lets the server decrypt every message, text or file, which conflicts with the zero-knowledge claim. Should be handled as a separate change.
- `mcp/` does not build; handled in sub-project 2, which will build on the file-aware `shared/` API added here.
